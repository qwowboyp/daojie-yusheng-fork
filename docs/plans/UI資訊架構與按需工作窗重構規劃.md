# UI 資訊架構與按需工作窗重構規劃

日期：2026-09-08。狀態：使用者已批准，核心工作區與導航已實作，程式門禁與工作窗瀏覽器驗證完成；不修改玩法、協定或權威資料。

### 本次實作

- 以完整地圖主舞台取代預設固定三欄；常用入口為交互與行動、背包、修行、任務與全部功能；聊天在自己的窗頭收合。其餘功能按既有任務分類進入同一工作區，同類分頁共用原本的面板與狀態。
- 人物生命／真氣與境界維持 HUD；人物詳細資料移入概況，系統與協助集中。聊天可收合，切換分類不重建頻道與輸入。
- 背包點選物品即可在同窗看候選與已裝備物品，主操作沿用原回呼；完整詳情保留原有數量、丟棄、來源與特殊表單。手機可返回原清單、原選取與焦點。
- 技藝入口重用既有共用工作臺；營造與指向性行動返回地圖。關窗不取消伺服器活動。任務、社交、坊市與世界保留原有業務權限與請求。
- 原交互、行動隊列與隊伍浮窗統一掛入遊戲層，保持原實例與偏好；管理工作窗覆蓋浮窗，詳情與確認視窗仍在上層。
- 新手導覽已調整入口、準備動作與正式繁體文案。測試使用實際前端入口和正式面板 fixture；不把未登入背景或生成圖片當成正式玩家畫面。

可重跑驗證：`pnpm verify:client`、`pnpm --filter @mud/client proof:game-workspace`。尚未做實體 iPhone／Safari、讀屏器或真實玩家任務成功率調查；下方相關驗收仍是後續實機與使用者研究項目。

## 1. 判斷修正：問題是資訊架構，不只是小字

上一輪把主題契合、視覺辨識與操作佈局合成 6/10，掩蓋了遊戲介面最重要的問題。紙墨風格與元件能力可以保留，但不能替不合理的預設佈局加分。

目前桌面配置較像同時展開的管理後台：多組面板永久占位、主次關係弱、分類名稱和內容不一致。只放大字體、調整留白或把每個面板原封不動改成浮窗，不足以解決問題。

「整體 0 分」並不是可重現的專業量尺：既有功能、快捷入口與部分鍵盤支援仍有價值。更準確的結論是：**預設佈局與導航架構不及格，需要重組，而非美化。** 不以另一個任意總分取代這個判斷。

### 已知證據與限制

- 本機 1440×900、未登入外框取樣：左欄 520px、右欄 680px，中欄 240px；其中 `game-stage` 寬 154px。1920×1080 時中欄為 720px。這證實預設尺寸對中型桌面不友善，但不是實際遊戲內容的完整驗收。
- 手機外框已有主分頁與巢狀分頁；部分按鈕字體僅 9px。縮小只是資訊過載的表徵，不是根因。
- 已有 `actionQueue`、`interactionList`、`party` 三類浮窗，預設啟用，並非「尚未實作浮窗」。重構應整合、取代重複呈現，不再疊一套入口。
- 正式站登入頁已觀察；尚未進行真實玩家登入後流程、實機 Safari、讀屏器或新手可用性測試。沒有操作頻率遙測，不能宣稱某菜單必然最高頻。

## 3. 哪些主張成立，哪些需要反駁

### 成立

- 不應讓低頻管理面板永久瓜分主舞台。
- 管理功能按需開啟，同一工作情境共享窗口、分頁與狀態。
- 菜單應先讓人辨認「我要做什麼」，不能按程式模組或歷史掛載位置分類。

### 不成立或有條件

以下也反駁這個方向容易衍生的極端做法，並非把「全部隱藏」或「所有東西都做浮窗」當成使用者原話。

1. **「菜單越小越好」不成立。** 視覺占位可以小，但觸控命中區與文字不能跟著縮。手機主要操作以約 44px 命中區作設計目標；不是把 44px 說成所有網頁情境的 WCAG AA 硬門檻。
2. **「全部藏起來才現代」不成立。** 戰鬥目標、生命資源、目前行動、必要隊伍資訊與任務追蹤需要持續可見。MUD 的文字情報也是玩法，不為了大地圖而全部隱藏。
3. **「同類全部做分頁」不成立。** 分頁適合互斥工作；裝備與候選物、配方與材料、買單與費用需要同時比較，應用同窗分區，不要求記住前一頁數值。
4. **「桌面浮窗直接縮成手機浮窗」不成立。** 手機應採有返回層級的工作頁或底部面板；不讓玩家管理重疊窗口、拖曳細小標題列。
5. **「一窗或兩窗上限」不是普遍法則。** 約束的是任意遮疊，而非必要資訊數量。物品工作區可以同時有背包、裝備、詳情三個區塊。
6. **「一個功能只能有一個入口」不成立。** 應是一個正式工作區、多個有意義的直達入口。地圖互動、快捷列、任務指引可以進同一頁，不複製實作、資料或選取狀態。

## 4. 推薦方向：主舞台＋情境工作區

這是資訊架構重組，保留既有像素仙俠、紙墨與低飽和主題，不另做重裝飾國風皮膚。

### 四層分工

| 層 | 內容 | 行為 |
| --- | --- | --- |
| 主舞台 | 地圖、角色、目標與附近可互動對象 | 不再為關閉的管理面板保留大塊固定欄位 |
| 持續摘要 | 必要生命資源、當前活動／隊列摘要、任務追蹤、隊伍、聊天摘要 | 精簡、可收合；詳細資料按需；緊急狀態不得被管理頁悄悄遮掉 |
| 管理工作區 | 背包裝備、修行、製作、任務日誌、社交、坊市等 | 點入口才開；同一任務所需資料並置；記住分頁、篩選、捲動與選取 |
| 短暫詳情／確認 | 物品詳情、數量、費用、確認、錯誤 | 有明確返回；不堆出第四、第五層巢狀對話框；資產確認仍保留 |

### 桌面構圖草案

```text
┌──────────────────────────────────────────────────┐
│ 玩家／生命／靈力                    區域／小地圖   │
│                                                  │
│                 地圖與場景                        │
│  隊伍／目前目標                    任務追蹤摘要    │
│                                                  │
│ 聊天摘要       當前活動／可用動作      緊湊功能入口 │
└──────────────────────────────────────────────────┘

點「背包」→ 打開物品工作區：
┌──────────────────────────────────────────────────┐
│ 物品與裝備                         搜尋／收合／關閉│
│ 類別與篩選 │ 物品清單 │ 詳情與差異／目前裝備      │
│            │          │ 合法操作／費用／結果       │
└──────────────────────────────────────────────────┘
```

- 工作區可佔右側、中央或較大區域，依內容與螢幕決定；不硬規定所有窗口都是窄小卡片。
- 桌面可釘選必要參照，但不能把新版預設又組回目前六塊永久面板。
- 行動快捷列和管理菜單分開；「配置技能」不是戰鬥時每次施放技能的必經入口。
- 入口保留圖示與短文字，快捷鍵是加速方式，不是唯一方法。不預先指派可能與移動、輸入框衝突的按鍵。
- 不在第一階段提供自由拖曳／縮放一切的 HUD 編輯器；先讓預設布局好用。

### 手機構圖草案

- 同一套功能分類與工作區，不是另一套同名不同內容的產品。
- 地圖上保留緊湊狀態、可收合追蹤、通訊及必要場景操作；手機快捷入口數量由原型試驗決定，不把全部主分類硬塞一列。
- 點入口後，簡單查看採底部面板；複雜製作、交易與裝備比較採接近滿版的工作頁。
- 手機可用「更多／全部功能」承接次要入口，但主功能要有文字名稱與明確分組；不可拿它當無分類垃圾桶。
- 返回順序為「詳情 → 原清單與原捲動 → 地圖」，不回到任意預設首頁。
- 戰鬥中查看管理內容不代表遊戲暫停。須持續提示必要權威狀態；不能用自動關窗遺失使用者輸入來掩蓋風險。

## 5. 初步功能歸屬原則

以下是待任務測試的分類草案，不是立即凍結的菜單數量或最終命名。各工作區不等於全部常駐一級入口。

| 工作區／入口 | 建議包含 | 刻意不放在這裡 |
| --- | --- | --- |
| 人物 | 身分、屬性、境界與狀態總覽；可直達裝備或修行對應內容 | 不把所有成長／物品操作都強迫從人物首頁進入 |
| 物品與裝備 | 背包、裝備、物品詳情及比較；背包有直接入口 | 任務、道友、坊市、功法管理不能再被叫成「行囊」的子類 |
| 修行 | 功法、相關技能配置、煉體等既有成長操作；具體邊界依現行機制核對 | 戰鬥中的即時施放與場景操作不藏在此窗 |
| 技藝 | 製作種類、配方、材料、條件與技藝隊列；同類活動用共同工作區 | 營造放置與地圖互動不能硬塞純表單；不得把行動隊列誤當技藝隊列 |
| 任務日誌 | 任務內容、進度、目標、合法接取／提交入口 | 世界地圖與附近互動仍屬場景層，不造「遊歷」大雜燴 |
| 社交 | 道友、隊伍、宗門、飛書的明確分頁與未讀摘要 | 隊伍即時狀態不因社交窗關閉而消失；聊天仍可直接開啟 |
| 坊市 | 交易相關列表、訂單與確認，完整費用與資產回饋 | NPC 商店保留場景入口，不默認遠端交易或繞過互動距離 |
| 系統與協助 | 設定、帳號、資源重載、引導、百科、更新紀錄等既有入口 | 玩家管理菜單不混入 GM 工具；不可暗改權限 |

入口收斂不能只做「舊名字換新名字」。需逐項列出舊入口、新工作區、直達別名、權限／位置條件、返回位置、狀態擁有者及驗收案例。

## 6. 技術與玩法不可變契約

1. 開窗、關窗、切分頁、收合追蹤只改顯示狀態，不能取消伺服器行動或製作；取消必須保留原有明確命令與回應。
2. 背包、金錢、裝備、功法、交易、隊列等依既有伺服器權威資料；不在新窗口建立第二套資產真源。
3. 同一活動的摘要與詳情消費同一來源，不能各自計時、各自判定完成。不同種類隊列不得只為視覺統一而混成一條。
4. 隱藏窗口可以減少渲染，但不能因此漏接必要狀態。重開、斷線重連、跨圖、權限改變要能由既有同步恢復正確內容。
5. 輸入、焦點、選取、捲動、排序、篩選與未送出表單有明確保留規則；高頻 patch 不重建整個工作區。
6. 模態確認才限制焦點；非模態工作窗不能不分情境鎖死整個遊戲。開啟焦點、Escape／返回、關閉後返回原入口一致處理。
7. 更換掛載處前盤點既有 host、mount、store、選擇器、導覽 prepare 動作與 proof，優先調整／刪除舊邏輯，不在舊 shell 外再包一層永久相容殼。
8. 預設本機 UI 偏好與伺服器權威狀態分開；不順手引入帳號跨裝置同步或資料庫新欄位。

## 7. 分階段交付與停損點

### A. 先完成資訊架構，不先美化

- 產出入口清單與任務路徑；識別名稱錯位、跨域分頁、重複狀態。
- 決定哪些持續可見、哪些按需、哪些情境直達。
- 用簡單線框測分類與找功能，不用裝飾／動畫讓缺點不明顯。

### B. 比較兩種布局方向

- 推薦：主舞台＋情境工作區，管理內容按需，必要摘要常駐。
- 對照：緊湊可收合側欄＋可釘選工作區，照顧偏好文字／數據管理的玩家；不是預設全開。
- 不推薦：所有功能都改成任意拖曳浮窗；也不推薦每次操作都覆蓋全畫面的手機式大型菜單。
- 本次已依使用者「先照你的計畫書執行」授權採用推薦方向；先前生成圖已撤回，不作為美術或功能驗收依據。

### C. 一條完整流程先行

- 優先驗證「物品選取 → 查看詳情與裝備差異 → 合法操作 → 結果 → 返回原位置」的完整工作區。
- 隨後接通「配方／條件 → 佇列 → 持續摘要 → 完成回讀」，驗證主舞台與管理窗不是兩套狀態。
- 流程成立再整合修行、社交、任務及坊市；共享窗口能力必須源於真實重複需求。

### D. 替換舊入口與驗收

- 新舊入口不長期並存；保留必要直達方式，但指向同一工作區。
- 更新導覽與現有 proof，不修改玩法規則來迎合新 UI。
- 實作階段按改動範圍執行 `pnpm verify:client`；如果觸及共享契約或服務端，再執行對應守門。本輪只有規劃文件，不執行產品 build／測試，也不做文件單獨提交。

## 2026-09-08 實機回饋後的補充規格

- 常駐列以「交互與行動」為第一個直接入口；聊天的收合控制放在聊天窗內，收合後保留一行標題及展開按鈕，不卸載頻道、訊息或輸入框。
- PC 的工作窗、聊天、人物摘要、行動隊列及正式詳情／確認彈窗可拖曳與縮放，各功能記住自己的位置和尺寸。工作窗最小為 360×320 邏輯像素；畫面不足時以可用畫面為上限，內容區負責捲動。
- 內容依工作窗寬度回應。背包窄窗改為完整道具名稱與「數量：…」清單，長名稱換行；選取後可查看詳情、執行原操作並返回清單。放大後恢復背包與裝備比較的雙欄呈現。
- 手機人物摘要預設精簡，透過展開／收合圖示切換境界與修為資訊。生命與靈力數值直接放在對應進度條內，以「命：目前 / 上限」與「靈：目前 / 上限」單行顯示。
- 手機短暫說明在外部點擊、觸控拖動、捲動及切換工作窗時收起；正式物品詳情彈窗維持自己的關閉流程。

實機裁切的根因是浮窗移入縮放的設計畫布後，將已縮放的畫面座標再次寫成 CSS 座標，導致浮窗越界；聚焦越界控制時又捲動了整個畫布。位置與拖曳需使用同一套邏輯座標，畫布使用不可捲動的裁切，面板內容各自捲動。回歸驗證須明確關閉桌面觸控模擬，涵蓋 3727×2233 畫面、重複刷新、邊界拖曳、縮放與聚焦，不以手機模擬通過推定桌面正確。
